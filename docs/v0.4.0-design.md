# v0.4.0 DNAT development design

## Stage 1: parser only

The six-field template mirrors the existing SNAT style. TCP/UDP single ports only; explicit destination address and incoming WAN interface are mandatory. WAN_IP resolves to the validated primary address. Duplicate enabled tuples are rejected. Disabled entries are validated. Existing SNAT/general formats and production engine remain unchanged.

The parser generates proposed NAT rules, not forwarding permissions. It does not establish whether the internal address is a valid LAN host, whether an external address is routed, or whether a native forwarding rule conflicts. Do not deploy parser output manually.

## Stage 2: read-only hardware discovery

Inspect native NAT PREROUTING, its referenced chains, filter FORWARD and referenced chains, and existing port-forwarding rules (redact all private deployment data before publication). Establish native precedence and whether the firmware already accepts DNAT state, and inspect relevant INPUT behaviour if a target is router-local. Verify conntrack match support and actual canonical rule output before choosing a policy.

## Stage 3: reconciliation design

Proposed separate AI_NAT_DNAT chain in PREROUTING, with a single managed jump. Validate both files completely before mutation. Use one NAT-table transaction for SNAT and DNAT where both need changes; avoid rewriting unchanged chains. Define precedence and refuse ambiguous conflicts rather than silently shadow native forwarding. No broad FORWARD accept rule and no blanket filter flush. If native forwarding is insufficient, design narrowly scoped forwarding permissions and safe ordering before enabling them; NAT and filter table commits are not one atomic operation. Consider stale conntrack mappings when removing or changing rules.

An empty/disabled DNAT configuration must not create inbound access. AUDIT must remain read-only. DISABLED must clean managed state without WAN validation. Existing v0.3.0 deployments need a documented migration path and rollback. No Docker changes anticipated.

## Acceptance

Software: existing SNAT regression suite, DNAT parsing/duplicates, full validation before writes, conflict handling, independent chain drift, idempotency and cleanup. Hardware: read-only inspection, restricted isolated test service, external connection and negative tests, unchanged native policies, firewall restart recovery, hardware offload evidence. Test additional addresses only when routing is confirmed. No hairpin or IPv6 support in this initial scope.
