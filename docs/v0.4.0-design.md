# v0.4.0 DNAT development design

## Stage 1: parser only

The eight-field template supports source CIDRs, TCP/UDP/both, port lists and ranges with preserved ports, and single-port translation. Overlapping enabled tuples including source intervals are rejected. Disabled entries are syntax-checked. General configuration accepts an optional interface allowlist during development; live engine is unchanged.

The parser generates proposed NAT rules, not forwarding permissions. It does not establish whether the internal address is a valid LAN host, whether an external address is routed, or whether a native forwarding rule conflicts. Do not deploy parser output manually.

## Stage 2: read-only hardware discovery

Read-only inspection on stock firmware found native destination-specific port-forwarding chains and an existing FORWARD conntrack DNAT acceptance rule, with nonzero packet counters. UPnP chains were empty at inspection. Native filter rules remain untouched; custom forwarding must still be hardware-tested. No private deployment information is retained here.

## Stage 3: reconciliation design

Proposed separate AI_NAT_DNAT chain with one jump at the end of PREROUTING, preserving native precedence. SNAT remains first in POSTROUTING. Destination validation must reject local, special, broadcast, WAN and management destinations and require an explicitly allowed routed interface. Native conflicts must account for inherited address, protocol, port and source matches; unknown formats fail conservatively. Validate both files completely before mutation. Use one NAT-table transaction for SNAT and DNAT where both need changes; avoid rewriting unchanged chains. Define precedence and refuse ambiguous conflicts rather than silently shadow native forwarding. No broad FORWARD accept rule and no blanket filter flush. If native forwarding is insufficient, design narrowly scoped forwarding permissions and safe ordering before enabling them; NAT and filter table commits are not one atomic operation. Consider stale conntrack mappings when removing or changing rules.

An empty/disabled DNAT configuration must not create inbound access. AUDIT must remain read-only. DISABLED must clean managed state without WAN validation. Existing v0.3.0 deployments need a documented migration path and rollback. No Docker changes anticipated.

## Acceptance

Software: existing SNAT regression suite, DNAT parsing/duplicates, full validation before writes, conflict handling, independent chain drift, idempotency and cleanup. Hardware: read-only inspection, restricted isolated test service, external connection and negative tests, unchanged native policies, firewall restart recovery, hardware offload evidence. Test additional addresses only when routing is confirmed. No hairpin or IPv6 support in this initial scope.

## Standalone destination validator

`router/dnat-validate.sh` reads canonical parsed DNAT rules on stdin and accepts three arguments: allowed interface CSV, logical WAN interface and physical WAN interface. Empty rules require no allowlist. For active rules it rejects unsafe interface names, local/broadcast addresses and routes, non-direct or unavailable routes, and destinations outside usable hosts on assigned interface subnets. Initial scope excludes routed downstream networks and /31 or /32 LAN subnets. The caller must supply verified current WAN interface identities. Ordinary route lookups are not proof of ingress policy routing behaviour; hardware checks and integration remain pending. No firewall writes or host probes are performed. Revalidate before each transaction; network state can still change concurrently.

## Standalone native conflict detector

`awk -v desired_file=desired.rules -f router/dnat-conflicts.awk desired.rules native.rules` analyses metadata-mode desired rules and a full `iptables -t nat -S` snapshot. It follows PREROUTING chain jumps with inherited source/destination intervals, protocol, input interface and destination-port intervals. The controller-owned unconditional PREROUTING jump is excluded; ownership/reference checks remain an integration requirement. Native DNAT, REDIRECT and NETMAP overlap and unsupported potentially overlapping matches/targets or goto are rejected unless explicitly forced per rule. Cycles, missing chains, ownership violations, malformed input and analysis limits remain fatal. Only supported positive predicates establish disjointness; unknown match options are opaque. RETURN and earlier terminal rules are not used to subtract traffic sets, so conservative false positives are possible. No rules are changed. This is not a general iptables interpreter; multiport, negation and arbitrary extension syntax are intentionally unsupported when relevant. Dynamic native rules require rechecking snapshots before transaction commit; races cannot be fully eliminated. Existing conntrack entries and live conflicts after a native change require separate operational handling. No raw deployment snapshots are committed.

## Per-rule Force override

The eighth field is mandatory: 0 for strict validation (all examples), 1 for administrator-authorised native conflict overrides. The parser validates every entry including disabled ones and still rejects managed overlaps. With `-v metadata=1`, DNAT output is `Force|source line|canonical rule`, emitted only after full successful validation; ordinary output remains canonical. Integration must parse once in metadata mode, derive canonical rules from the same records, and pass all canonical rules to destination validation and transaction generation. Never pass metadata to iptables. The conflict detector consumes metadata records and logs warnings on stderr for each forced candidate and overridden finding. A strict candidate is unaffected by other forced candidates. Native precedence remains unchanged, so forced rules may be shadowed. Force is not a general validation bypass; snapshot integrity, ownership, recursion/work limits, malformed desired input, destination safety, WAN checks and transaction checks remain mandatory. Warnings will be surfaced in both AUDIT and ENFORCE when integrated. No live enforcement yet.
