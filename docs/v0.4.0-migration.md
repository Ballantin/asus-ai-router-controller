# v0.3.0 to v0.4.0 migration and rollback

Use a maintenance window with local administrator access and a firmware settings backup. Pin the release candidate by full commit SHA and record its successful CI run. Use an independent administrator session for the runbook. The scheduler's restricted SSH key invokes the controller and must only be used for scheduled reconciliation.

## Before changing anything

1. Confirm the running engine version, stock firmware and tool versions. Verify the primary WAN address and default route agree with the local configuration. Verify the allowed destination bridge using the actual route, connected subnet and address inventory. Additional public addresses require confirmed upstream routing.
2. Capture private baseline snapshots of `iptables -t nat -S` and `iptables -t filter -S FORWARD`. Record native application connectivity, hardware acceleration state, scheduler settings and current controller mode. Keep these snapshots local.
3. Pause the scheduler with `docker stop router-controller` on the AI board. Confirm it has stopped and allow any already-started router command to finish. Also pause independent controller invocations. Keep the existing restricted SSH key, mounted volume and image available.
4. Create a new, private backup directory. Copy the active v0.3.0 scripts, parser, general configuration and SNAT rules with permissions preserved. Include any existing DNAT files from earlier staging and record which files were absent. Verify each backup with `cmp -s`; keep a separate copy accessible from the administrator workstation.

## Stage and audit

1. Stage the pinned commit's `nat-controller.sh`, `wan-check.sh`, `dnat-validate.sh`, `nat-config.awk` and `dnat-conflicts.awk` on the router in a private directory. Verify checksums against the pinned source. Run `sh -n` for each shell script with the router's shell. Check both AWK files using the router's AWK and valid fixtures from the pinned commit.
2. Copy the live configuration and SNAT rules into staging. Change only the staged mode to AUDIT initially and create an empty `dnat-rules.conf` (a comment-only file is sufficient). Leave any DNAT interface policy unset until you have verified the intended destination bridge. The runtime policy defaults to `WITHDRAW_UNSAFE`.
3. With the scheduler stopped, install each file via a same-directory temporary file and rename. Shell scripts need owner execute permission. Configuration and AWK files should be owner-readable with mode 600. Install the controller entry point last. The controller uses fixed production paths, so running the staged entry point directly still reads live files.
4. Run `/jffs/custom/nat-controller.sh` once from the independent router session. Require exit 0. If drift is reported, inspect the complete desired SNAT proposal and resolve unexpected differences before continuing. Compare full NAT and FORWARD snapshots to confirm the AUDIT run made no changes.
5. After approval for ENFORCE, switch mode atomically and run once with the empty DNAT configuration. Require correct SNAT, no owned DNAT chain or jump and unchanged native rules. A second run should report `IN_SYNC`. Run the [hardware acceptance plan](acceptance-tests.md#v040-hardware-acceptance-plan) with separate approval for isolated test mappings and firewall restart.
6. Resume the scheduler using `docker start router-controller` only when the selected mode and active configuration are approved. Check the next two cycles and compare their duration with the 15-second SSH timeout. Record any `SKIP`, timeout, verification failure or `DNAT_WITHDRAWN` as an event requiring investigation.

## Roll back

1. Stop the scheduler and wait for in-flight invocations as above. Remove temporary test services or otherwise stop accepting test traffic. Preserve the failure evidence privately.
2. While the v0.4.0 engine is still installed, atomically set the general configuration to `MODE=DISABLED`. Run the engine independently and require exit 0. Verify removal of both controller chains and their jumps, and check native NAT and FORWARD policy. A failed cleanup is a stop condition. Keep the scheduler stopped and investigate using local access before replacing the engine.
3. Restore the verified v0.3.0 files, removing only v0.4.0 additions that were absent from your backup. Install the prior engine entry point last. Restore the prior SNAT configuration and validate it against the current WAN. If WAN has changed since backup, stage the restored controller in AUDIT and resolve the difference before any enforcement.
4. Audit with the restored engine. After approved SNAT reconciliation, verify native rules and representative traffic, then resume the scheduler and confirm repeated `IN_SYNC` results. Record restored version, mode and evidence.

DISABLED removes the controller's SNAT as well as DNAT. Expect a service gap for managed flows during rollback. Existing conntrack entries can survive policy changes, so verify with new flows. Keep native rules and conntrack intact. If a concurrent native writer causes a verification error, capture fresh state and investigate before any retry. Replaying an old full-table snapshot can overwrite live ASUS state.
